# Habit Tracker — Project Instructions

## 1. Назначение проекта

Habit Tracker — персональное mobile-first приложение для ежедневных повторяющихся действий и привычек.

Проект предназначен не для обычных одноразовых задач, а для действий, которые нужно выполнять регулярно.

Примеры:

- английский;
- гитара;
- зарядка;
- чтение;
- отжимания;
- прогулка;
- вода;
- медитация.

---

## 2. Конечная цель

Создать быстрое, удобное мобильное приложение привычек с аккаунтами, синхронизацией между устройствами, статистикой, личным прогрессом и добровольной социальной составляющей.

Основной сценарий использования — телефон.

Приложение должно быть доступно:

- через Web;
- как установленное PWA на телефон;
- по собственному production-домену.

Ключевое требование проекта — скорость. Пользователь должен нажать на иконку и почти сразу получить рабочий экран без заметных зависаний и ожидания.

---

## 3. Основной принцип

Habit Tracker работает с повторяющимися ежедневными активностями.

Не нужно превращать его в обычный todo-list.

Главная сущность проекта — регулярное действие и история его выполнения.

---

## 4. Типы привычек

Привычка может иметь разные способы выполнения.

### Binary
Просто выполнено / не выполнено.

Пример:
- сделал зарядку;
- позанимался английским.

### Count
Количество повторений.

Пример:
- 10 отжиманий;
- 20 приседаний;
- 8 стаканов воды.

### Duration
Время выполнения.

Пример:
- чтение 30 минут;
- гитара 20 минут;
- английский 15 минут.

### Target
Пользователь задаёт целевое значение.

Пример:

Гитара  
Цель: 30 минут

Сегодня выполнено: 18 / 30

---

## 5. Ежедневная работа

На главном экране пользователь должен быстро видеть:

- сегодняшние привычки;
- прогресс по каждой;
- общий прогресс дня;
- серию выполнения;
- возможность изменить количество или время;
- быстро отметить привычку выполненной.

Главный экран должен быть максимально удобен для телефона и требовать минимум действий.

---

## 6. Скорость и производительность

Скорость является одним из ключевых продуктовых требований.

Цель UX:

**нажал на иконку → приложение открылось → сегодняшние привычки сразу доступны.**

Нельзя считать нормальным UX, если пользователь регулярно ждёт загрузку приложения или основных данных.

При проектировании нужно стремиться к:

- минимальному времени первого открытия;
- быстрому повторному запуску;
- мгновенной реакции интерфейса на отметку привычки;
- локальному кешу последних актуальных данных;
- загрузке второстепенной информации после появления основного экрана;
- минимальному количеству тяжёлых запросов при старте;
- оптимизации мобильной сети;
- отсутствию тяжёлых анимаций, блокирующих интерфейс;
- сохранению работоспособности основного экрана при кратковременных проблемах с сетью.

Для пользователя синхронизация должна происходить максимально незаметно.

Сервер остаётся source of truth, но приложение не должно каждый раз выглядеть пустым, пока ждёт ответ сервера.

---

## 7. Статистика

Существующая идея месячной статистики сохраняется и развивается.

Нужно показывать:

- процент выполнения;
- количество выполненных дней;
- серии;
- лучший результат;
- текущую серию;
- среднее выполнение;
- статистику по неделям;
- статистику по месяцам;
- статистику отдельных привычек.

Статистика должна мотивировать, а не перегружать пользователя.

---

## 8. Пользователи

Проект должен поддерживать полноценные аккаунты.

Планируется использовать проверенную модель авторизации по аналогии с Genealogy:

- логин;
- пароль;
- серверная сессия;
- 2FA при необходимости;
- восстановление доступа;
- роли.

Авторизацию не нужно буквально копировать без проверки, но архитектурно можно использовать проверенные решения Genealogy.

---

## 9. Синхронизация

Основные данные должны храниться на сервере.

Пользователь может открыть Habit Tracker:

- на телефоне;
- на компьютере;
- на другом устройстве;

и видеть одинаковые данные.

LocalStorage больше не должен быть основным source of truth.

Локальное хранение используется как кеш, offline fallback и способ обеспечить быстрый UX.

---

## 10. PWA и мобильное использование

Проект должен быть mobile-first.

Особое внимание:

- touch-интерфейсу;
- свайпам;
- крупным кнопкам;
- скорости;
- safe areas;
- Android;
- iPhone;
- установке на главный экран;
- offline fallback;
- корректному обновлению PWA.

PWA должно ощущаться как приложение, а не как сайт.

---

## 11. Социальная система

Пользователь может по желанию делиться частью результатов с другими пользователями.

Возможные элементы:

- друзья;
- группы;
- сравнение прогресса;
- месячный рейтинг;
- серии;
- достижения;
- соревнования.

Социальные функции не должны мешать пользователю, который хочет использовать приложение полностью приватно.

---

## 12. Звёзды и рейтинг

Можно использовать простую систему мотивации.

Например:

выполненная привычка
→ очки

выполненный день
→ бонус

серия
→ дополнительный бонус

За месяц пользователь получает итоговое количество звёзд.

Можно показывать:

- свои звёзды;
- результат прошлого месяца;
- результат друзей;
- рейтинг группы.

Система должна поощрять постоянство, а не количество бессмысленно созданных привычек.

---

## 13. Админка

Admin-панель предназначена для управления системой.

Возможности:

- пользователи;
- блокировка / разблокировка;
- состояние аккаунтов;
- базовая статистика использования;
- управление группами;
- системные настройки;
- диагностика.

Администратор не должен без необходимости видеть приватное содержимое привычек пользователей.

---

## 14. Приватность

Пользователь сам определяет, какие данные доступны другим.

Привычка может быть:

- private;
- visible to friends;
- visible to group.

По умолчанию личные данные должны быть приватными.

---

## 15. Домены и production

Проект должен иметь собственный production domain.

GitHub является source of truth для кода.

Production должен работать по общей модели наших проектов:

GitHub
→ CI
→ PROD

Конкретная схема deployment и Runner настраивается отдельно.

Старый Vanilla JS проект рассматривается как прототип UX и функциональной идеи.

Новая версия должна иметь нормальную структуру проекта.

Рекомендуемое направление:

- React;
- TypeScript;
- backend API;
- PostgreSQL;
- Docker;
- PWA;
- серверная авторизация;
- migrations;
- health checks;
- backup;
- production environment.

Точный стек можно уточнять перед реализацией.

---

## 17. Модель данных

Основные сущности:

- User
- Habit
- HabitEntry
- HabitTarget
- HabitType
- Friendship
- Group
- GroupMember
- Achievement
- MonthlyScore

Habit хранит описание привычки.

HabitEntry хранит выполнение конкретной привычки в конкретный день.

Это позволяет строить статистику без изменения самой привычки.

---

## 18. История привычки

Изменение цели привычки не должно ломать старую статистику.

Например:

Январь:
гитара — 10 минут

Февраль:
гитара — 20 минут

Март:
гитара — 30 минут

Исторические записи должны сохранять реальные значения того периода.

---

## 19. UX

Старый интерфейс не считается конечным.

Новый интерфейс проектируется заново.

Приоритеты:

- мобильность;
- скорость;
- минимум действий;
- понятный прогресс;
- приятные анимации;
- мотивация;
- быстрый ввод;
- визуальная статистика.

Киберпанк-дизайн старой версии не является обязательным.

---

## 20. Принятые продуктовые решения

На текущий момент утверждено:

- проект предназначен для повторяющихся привычек, а не обычных задач;
- основной клиент — телефон;
- приложение должно работать как PWA;
- приложение должно открываться быстро и давать доступ к сегодняшним привычкам без заметного ожидания;
- данные должны синхронизироваться через сервер;
- сервер является source of truth, а локальное хранение используется для быстрого UX и offline fallback;
- нужна полноценная авторизация;
- нужны binary, count и duration привычки;
- цель привычки может иметь количество или время;
- нужна месячная статистика;
- нужна социальная составляющая;
- социальные функции должны быть добровольными;
- нужна система звёзд / рейтинга;
- нужна Admin-панель;
- старый Vanilla JS проект считается прототипом;
- интерфейс будет переработан;
- production должен получить собственный домен.
